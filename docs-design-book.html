The shape of it

One teacher, many students, one library

A Carnatic vocal teacher in India records lessons; students in a dozen time zones listen to what has been given to them. Everything else in the app follows from those two sentences.

There are exactly two roles. A teacher sees everything and is the only person who can add anything. A student sees the songs assigned to them, the recordings and notes shared with them, their own lesson history and their own classes — and nothing else, ever, including through a guessed URL.

The whole app is server-rendered HTML. Every core flow — assigning a song, logging a lesson, sharing a recording, rescheduling a class — is a plain form post that works with JavaScript switched off. Three small scripts add what markup cannot do: playback speed and the A–B loop, browser recording with MP3 encoding, and remembering which collapsible sections you left open.

How a request moves

One Worker, two stores

There is no application server and no origin. A request reaches a Cloudflare Worker, which reads the session cookie, asks D1 for rows, and — for audio — streams bytes out of R2 after checking that this listener is allowed to have them.

The data model

Twelve tables, two of them joins

Songs live in sections for historical reasons — the table predates the word "song" being settled on — and a recording belongs to a song, not to a student. That single decision is what lets one reference take serve everyone learning the piece.

Who hears what

Shared by default, given by name when it matters

A recording or note is either for everyone learning the song (visibility = 'shared') or for a named set of students ('chosen', with rows in the share table). One item can go to any number of students without being copied.

The check, in full

async function studentMaySee(env, studentId, item, kind) {
  if (item.visibility !== 'shared') {
    const given = await …SELECT 1 FROM ${kind}_shares
                      WHERE ${kind}_id = ? AND student_id = ?;
    if (!given) return false;
  }
  return …SELECT 1 FROM assignments
           WHERE student_id = ? AND section_id = ? AND archived_at IS NULL;
}

Anything that is not exactly 'shared' is treated as restricted. That is deliberate: a row left behind by a half-finished upgrade is checked against an empty share list and comes back false. The failure mode is a student who has to ask for a recording, not a student who hears one they shouldn't.

Row three is the newest rule and the one worth understanding. A student sees every recording on their songs; the ones not given to them appear named but unplayable, under "Not yet shared with you". They can see the library exists and ask for a take; the teacher, opening the same page, gets an Unlock button on each locked row and a Lock on each open one.

Time and the schedule

India is fixed; the students move

Every class is anchored to a wall time in India. India has never observed daylight saving, so IST is a fixed UTC+05:30 and turning "Tuesday 7pm" into an instant is arithmetic — no library, no rule table that goes stale. 

export function istToInstant(date, time) {
  const [y, m, d] = date.split('-').map(Number);
  const [hh, mm] = time.split(':').map(Number);
  return new Date(Date.UTC(y, m - 1, d, hh, mm) - 330 * 60_000);
}

The students are the ones who move, so their side is computed per occurrence with Intl.DateTimeFormat, which knows each zone's rules. users.time_zone holds an IANA name — never a numeric offset, which is wrong for half the year anywhere that changes its clocks.

  • Occurrences are computed on read, never stored. Editing a slot corrects every future class at once, and there is nothing stale to migrate.
  • The scan runs wider than the window. A class moved from Friday into the following Sunday is generated while scanning Friday; without a ±14-day scan and a trim by final date, it vanishes from the week it landed in.
  • A student who isn't active has no future classes — but every class they already had stays on the calendar, marked with their status.
  • test-tz.mjs asserts against real transitions in New York, London and Sydney, plus date rollover and the moved-across-a-boundary case.
The trap this avoids. Storing "+5:30" or "-5" per student. Twice a year half the roster would be an hour wrong, and the bug would look like the student's fault.
Upgrading a database

Four steps, in this order

CREATE TABLE IF NOT EXISTS does nothing to a table that already exists — so a column added in a new version never arrives, and the first index over it takes the whole app down at startup. That happened once. The fix is an ordering, and the container runs all four on every start.

  1. schema.sql — tablesCreates whatever is missing. No indexes here, ever.
  2. scripts/sync-schema.mjs — columnsParses the column list out of schema.sql, compares it to PRAGMA table_info, and issues ALTER TABLE ADD COLUMN for the difference. Only ever adds.
  3. indexes.sql — indexesNow that the columns are guaranteed to exist.
  4. backfill.sql — dataWhen the meaning of existing rows changes. Each statement is written so its own effect removes the rows it selects, which is what makes a second run a no-op.

The same four commands work against Cloudflare with --remote. Adding a column to schema.sql is the whole task: step 2 finds it. That is how recordings.description, notes.title and users.phone reached a running database with no hand-written migration.

The media pipeline

Recorded in a browser, played on an old iPhone

Browsers disagree about recording formats: Chrome and Firefox produce WebM/Opus, Safari produces MP4/AAC, and Safari could not play WebM until 18.4. A lesson recorded in Chrome would have been silent on an older iPhone — the exact device a student is most likely to practise from. 

MediaRecorder  →  decodeAudioData  →  lamejs (96 kbps mono MP3)  →  POST /api/recordings
                                          ↓ yields between blocks
                                     page stays responsive
  • Audio is re-encoded in the browser before upload: one format, plays anywhere, about 0.7 MB a minute.
  • If conversion fails for any reason the original is kept rather than the take lost.
  • Video is left alone and capped at two minutes.
  • Uploads go through the Worker — simpler than presigned URLs and needs no extra R2 credentials. The ceiling is Cloudflare's 100 MB request body; the app refuses anything over 90 MB with a clear message.
  • Playback asks R2 for byte ranges, so seeking in a 90-minute file doesn't download it.
Keeping it

The dump is the manifest

Two stores fail in different ways, so the backup has to answer both — and the interesting part is not that it copies things, but that the database decides what gets copied.

D1's Time Travel is always on, costs nothing, and restores the database to any moment in the last seven days on the free plan. It is the right first answer to "I deleted the wrong student", and no answer at all to a deleted database or a lost account. R2 has no versioning to fall back on. So there is a weekly job, and it writes outside Cloudflare.

It does not run inside the Worker. The free plan allows 10 ms of CPU and 50 subrequests per invocation, cron triggers included; serialising a few megabytes of rows spends the first and twelve table reads plus the writes crowd the second. That design works at twenty students and fails intermittently at eighty — the worst possible failure curve for a backup. And a copy held inside the account it protects does not answer the failure that matters.

What the manifest buys

  • It is incremental without keeping any state. The first run seeds the library; every later run fetches the week's new takes, because the keys already on disk are simply skipped.
  • An orphan is never mistaken for data. A file no row references — usually an upload that failed after the bytes were written — is not copied, because nothing will ever ask for it again.
  • A missing file is found here, not in a lesson. A key the database expects and R2 does not have is silent data loss until a student presses play. The backup reports it and fails the run.
  • It copies forward and never back. A recording deleted from R2 stays in the backup. No code path in the program deletes a media file.

Reaching R2

R2 speaks S3, which means SigV4-signed HTTPS. The choices were the AWS SDK — tens of megabytes for four verbs — rclone, which is a binary to install on a Mac with no Homebrew, or aws4fetch: 88 KB, no dependencies of its own. The third, and scripts/lib/r2.mjs is HEAD, GET, PUT and LIST over it in about 180 lines.

The token is an R2 API token, which is not the Cloudflare token wrangler uses; they are not interchangeable, and the error when you confuse them is a bare 403. It is scoped Object Read only: the thing that runs unattended every week cannot damage the bucket it is protecting. Restoring needs a separate write token, which is the point of the read-only one.

Four refusals

Each is a way this class of program fails quietly, turned into a stop.

isn't there		Writing into a folder Drive isn't syncing produces a backup that exists only on that Mac — the exact failure the whole thing exists to prevent.

exceed the quota		Free Google Drive is 15 GB, shared with Gmail. A full Drive doesn't just stop the recordings — Drive stops syncing everything, dumps included. It copies no media and says by how much.
a download
is interrupted		Files land as .part and are renamed only once complete, so a half file can never be mistaken next week for a whole one.

Getting it back

  1. Time Travel first, if it is inside a weekwrangler d1 time-travel restore. No files involved, nothing to download.
  2. The databaserestore.mjs makes you type the database name, drops in reverse order under PRAGMA defer_foreign_keys, applies the dump, re-creates the indexes — they are not in the dump — and compares every table's row count against the backup.
  3. The recordingsrestore-media.mjs does nothing without --yes, and leaves alone any object R2 already has. Restoring into a half-good bucket is the common case, and overwriting the good half with an older copy turns a partial loss into a total one.
  4. Then play somethingA recording plays only if its bytes came back under the right key. That is the step that actually tests the media backup, and it is the last step of the quarterly drill.
The drill is not optional, and it has already paid for itself. Restoring into a deliberately damaged database failed with no such table: main.users — dropping tables in creation order leaves a child's foreign key pointing at a dropped parent. That bug would otherwise have been found during a real loss, which is the one moment it must not be.

Tokens first, one stylesheet, no framework
